# UcmTransferGraph 的 A800 评估方案

本文件定义测量方法，不是实测结果。实际功能范围、参数和命令以 `ucm-transfer-graph.md` 与实现附带的基准说明为准。

## 设备与接口

用户已确认：通过 POSIX 接口访问 Linux 文件路径（本地挂载或 NFS）；CPU 包括 x86 和 aarch64，计算设备包括 NVIDIA H100 和昇腾 910B3。目前没有可用的测试机器。具体客户端、版本、网络和挂载方式以后补充；不能从 A800 内部采用 NVMe 介质推导出主机能够直接访问 NVMe submission queue。

第一阶段的 graph 仅接受声明严格 Load 完成能力的后端。现有接入目标是启用严格模式的 POSIX psync，经健康包装层仍保留该能力；AIO、ASU 以及未知后端不开放。复制使用常规 CUDA/Ascend/simu stream，拒绝 IO Aggregation、GDR 和 SDMA Direct。以下涉及 AIO 的矩阵项仅是后续完成语义修复后的评估计划，不能在本版本开启 graph 测量。

严格模式中，逻辑超时会取消排队任务，但正在执行的同步 I/O 必须真正返回后才能释放 buffer。因此 NFS hard mount 卡住时，Wait 与停机也可能持续等待；不能用提前释放内存实现“硬超时”。

参考：[华为 A800 产品介绍](https://e.huawei.com/en/products/storage/ai-storage/oceanstor-a800)。官方整机带宽、IOPS 或推理案例不作为本改动的性能预测。

## 测量分为三层

| 层级 | 固定条件 | 可以回答的问题 | 不能推出的结论 |
| --- | --- | --- | --- |
| 计划微基准 | 相同请求形状、无真实 I/O | 构造/复用计划的 CPU 代价和内存上界 | A800 或端到端推理加速 |
| UCM simu + 真实文件后端 | 相同数据、目录类型、严格 psync、命中分布、并发 | 后端任务数量、CPU 时间、功能正确性和文件路径吞吐 | GPU/NPU 传输速度 |
| A800 + 实际 GPU/NPU | 相同模型、KV 布局、设备、协议、网络与负载 | KV 加载吞吐/尾延迟、TTFT、TPOT、吞吐与 CPU 的实际变化 | 未测试协议/模型/规模也有同样收益 |

必须分别标明模拟设备、真实文件系统和真实存储设备；本地 tmp 不能标为 A800。

## 性能假设

对一次包含 M 个 owner miss 的加载，设每次后端 task 管理开销为 C_task，每个 shard 必须执行的查找和描述符绑定开销为 C_bind。忽略尾批和 buffer 压力时，批大小 B 有：

```text
原管理开销 ≈ M * (C_task + C_bind)
新管理开销 ≈ ceil(M / B) * C_task + M * C_bind + C_plan_lookup + C_batch
```

优化仅减少可摊销的部分。缓存查找、数据读写、网络传输和 per-shard 工作仍需执行。后端即使接受一个 TaskDesc，内部也可能对每个 shard 打开/读取文件。

如果被消除的 CPU 管理阶段只占总时延比例 f，该阶段的加速为 s，则理想串行上界为 `1 / ((1-f) + f/s)`。真实流水线还会受到排队和资源竞争影响，不能将此公式当作实测。

吞吐上限受以下各段中的有效瓶颈限制：客户端网络、A800 分配给本工作负载的吞吐、文件协议、主机内存带宽、H2D 链路、CPU 提交能力。每段的方向、协议开销与共享流量必须单独考虑。

窗口参数首先从 8/16/32/64 shard 逐级尝试。默认样例参数只是起点。窗口越大不必然越快：整批 Wait 会延后快 shard 的可用时间，每批 fence 会增加设备同步成本。

## 公平对照

1. 同一二进制只切换 graph 开关，使用相同后端、batch 配置之外的资源参数与测试数据。
2. 固定 shard 字节数、tensorSizes、shard 总数、block 复用方式、并发、rank 排序与负载速率。
3. 分开报告准备数据、预热、测量和校验时间。当前基准的 wall throughput 明确包含请求准备和读后校验，Load-through-Wait 延迟则不含这些开销。后续若报告纯加载吞吐，需另采集并发请求整体加载区间，不能用各请求延迟之和代替 wall time；数据校验始终不能省略。
4. 轮换运行顺序（off/on 与 on/off），至少 5 个独立重复；每组给出原始结果及汇总，避免将单次尖峰当作提升。
5. 记录 requested hit ratio 和真实 hit/miss/owner 状态。命中状态会受访问顺序、容量和预取影响，不以配置值代替实测值。
6. Buffered I/O 可能命中 OS/客户端缓存；冷存储结果与热客户端缓存结果分开报告。不执行全机 drop_caches，以免干扰其他业务。
7. 直接 I/O 仅在所选客户端支持并满足对齐要求时启用。libaio 对特定文件系统的有效异步程度需实测，不能作为设备无关保证。
8. 使用单独创建的实验目录和随机命名文件，不扫描或重写已有生产缓存。实验完成保留原始报告，清理只能针对明确创建的实验目录。

## 最小矩阵

先用目标模型的真实 shard 布局，再以合成数据定位瓶颈：

| 因素 | 取值 |
| --- | --- |
| shard 大小 | 4、16、64、256 KiB，以及模型真实值 |
| 窗口 shard 数 | 1、8、16、32、64 |
| 请求并发 | 1、4、16，增加到目标业务并发 |
| DRAM 命中 | 0%、50%、100%，核验实际比例 |
| 后端 | 当前为严格 psync；AIO 须先修复完成语义并增加能力验证 |
| buffer 压力 | 宽松池、小池、请求总数据大于池 |
| 请求形状 | 固定形状、交替形状、超出计划缓存容量 |

不必一次跑完笛卡尔积：先固定真实配置比较，再围绕观测到的瓶颈改变一个因素。

## 必须输出的观测量

- 正确性：校验失败数、请求失败数、timeout、未收敛任务及重复完成数。
- 管理层：backend Load 调用数、owner miss shard 数、实际平均/最大 batch、计划命中/淘汰。
- 延迟：排队、后端等待、H2D 提交、H2D fence、端到端 P50/P95/P99，分别记录首批和整请求完成。
- 资源：CPU process time / GiB、峰值内存、最大在途 buffer 和任务、主机网络吞吐。
- 业务：固定负载下的 TTFT/TPOT、输出 tokens/s、调度等待与失败比例。

若当前实现/基准未提供某计数，明确标记 unavailable，并给出追加采集方式。不得填入按 B 推算的计数冒充真实采集。

## 启用决策

第一阶段保持默认关闭。上线前要求：相同负载下数据正确、资源有界、错误回收测试通过，且至少在目标场景中验证 CPU/GiB 或吞吐改善，同时尾延迟满足业务阈值。

若全命中、低并发或 batch=1 明显退化，可使用关闭开关回退，或在后续版本依据可信的形状/负载信息选择路径。不要因为批量提交计数下降就认定端到端加速。

## 已完成的软件验证（2026-10-22）

代码提交 `63ac2591` 的 [GitHub Actions](https://github.com/luomoduchu/unified-cache-management/actions/runs/39743377819) 已通过 Ubuntu 24.04.5 simu 构建、997 项启用的 CTest、可移植计划测试、指标回归及 19 项图执行器测试的 10 轮重复。1 项原有指标压力测试处于禁用状态。

两种顺序的 CacheStore/Posix/simu 冒烟运行均完成全数据校验。在每种模式仅 2 个请求、每请求 4 个 4 KiB shard、50% 命中的条件下，同样 4 个 backend miss，提交数从 4 次降至 2 次；[原始 JSONL](ucm-transfer-graph-ci-smoke.jsonl) 保留四行输出。运行顺序反转后，吞吐和延迟的优劣也反转，因此这里只确认批量机制有效，不给出性能提升百分比。

这些运行使用 CI 本地文件系统和模拟计算设备。A800、H100、910B3、aarch64 和设备故障恢复尚未测量，仍须按前述矩阵另行验证。
